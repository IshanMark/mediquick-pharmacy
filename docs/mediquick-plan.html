1Overview

The site replaces walk-in-only sales with a catalogue customers can search, a checkout with card or cash on delivery, and a prescription check that stops Rx-only medicines from shipping until a pharmacist approves. Everything runs on one XAMPP install, with no frameworks beyond Bootstrap, so every line can be explained in the report.

2Product requirements

Goals

  • Customers can find a medicine and place an order in under 3 minutes.
  • No Rx-only medicine is confirmed without an approved prescription on file.
  • Staff handle prescriptions, orders, stock and inquiries from one panel.
  • Admins can see who changed what, and when.

Assumptions

The brief allows added functionality when the assumptions are stated clearly.

  • One branch in Kurunegala delivers island-wide. Delivery is a flat LKR 350, and free over LKR 5,000.
  • Payments use the PayHere sandbox, so no real money moves. Cash on delivery is also offered.
  • For Rx orders, card payment happens after the pharmacist approves, so rejected orders never need a refund.
  • Notifications are in-app only. SMS and email are future work.
  • Roles are fixed (customer, staff, admin) and stored in one column. A custom permission builder is out of scope.
  • The cart lives in the PHP session and is emptied at logout.

Out of scope

  • Live payments, SMS gateway, live delivery-rider map, multiple branches, mobile app.

4System architecture

A classic three-tier setup. The browser only ever talks to Apache. PHP is the only thing that touches MySQL and the prescription files. PayHere confirms payments by calling the server directly, not through the customer's browser.

6Database plan

Twelve InnoDB tables in mediquick_db, normalised to 3NF. The ready-to-import script is at database/schema.sql in the project folder.

Design decisions

  • One users table with a role column. Customers, staff and admins log in the same way. Separate tables would repeat the login code three times.
  • order_items.unit_price is copied at order time. Changing a product's price later doesn't change old invoices.
  • Money is DECIMAL(10,2), never FLOAT, so LKR totals never pick up rounding errors.
  • CHECK constraints (price ≥ 0, stock ≥ 0, quantity > 0, rating 1–5) back up the PHP validation at the database level.
  • Foreign keys with ON DELETE rules. Deleting an order removes its items. Deleting a user keeps their audit rows (set to NULL). Customers are suspended rather than deleted, so order history survives.
  • Indexes on product name, generic name, orders.status and prescriptions.status: the columns used by search and the staff queues.
